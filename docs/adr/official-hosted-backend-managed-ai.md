# 第一版采用官方托管后端与 Managed AI/OCR

## 简要概括

第一版面向普通高中生。为了让用户无需申请、理解或保管模型与 OCR 供应商的 API Key，错题局选择由官方统一托管业务后端、用户数据和 AI/OCR 调用。BYOK 与自托管保留为未来开发者能力，不进入第一版。

## 状态

已接受

## 上下文

### 要解决的问题

错题局第一版需要保存错题、图片、标准答案、私人备注、复习状态和分享授权，并调用 OCR、实时语音和推理模型。目标用户是普通高中生，要求用户自行申请并配置多个供应商的 API Key 会显著增加使用门槛，也会让成本、密钥安全、故障处理和数据流难以统一管理。

同时，项目未来可能开放数据格式、SDK 或自托管能力，因此需要避免把业务数据直接建立在单一 AI 供应商的知识库中。

### 决策依据

- 普通高中生能否直接使用产品；
- 用户数据、供应商凭据和权限是否能被统一保护；
- OCR、语音和模型成本是否能被计量和控制；
- 业务状态是否掌握在错题局自己的系统中；
- 供应商未来是否可以替换；
- 第一版的开发和运维复杂度。

### 考虑过的选项

#### 选项 A：官方统一托管与 Managed AI/OCR

- 做法：错题局托管后端和用户数据，由服务端持有供应商凭据并统一调用 OCR、语音和模型服务。
- 优点：普通用户无需配置；可以统一计量、限流、重试、降级和保护密钥；便于保持一致的产品体验。
- 缺点：错题局承担供应商费用、滥用风险、服务运维和数据处理责任。
- 适用条件：面向普通消费者、需要持续 AI/OCR 调用的第一版。

#### 选项 B：用户自带 API Key

- 做法：用户自行申请供应商账号，并在错题局中配置 API Key。
- 优点：模型费用由用户直接承担，官方现金流压力较低。
- 缺点：对高中生门槛过高；密钥配置和供应商差异会破坏产品体验；难以提供稳定支持。
- 适用条件：开发者工具、重度专业用户或后期高级设置。

#### 选项 C：第一版同时支持官方托管、BYOK 和自托管

- 做法：从第一天实现多种部署和模型账户模式。
- 优点：选择最多，理论上覆盖更多隐私和成本需求。
- 缺点：显著增加认证、配置、测试、计费、升级和支持复杂度，超出原型 Demo 所需范围。
- 适用条件：产品已经验证，并出现明确的开发者、学校或隐私部署需求。

## 决策

我们将为第一版提供错题局官方统一托管的业务后端与 Managed AI/OCR，因为它最符合普通高中生低门槛使用、统一密钥保护、成本计量和稳定体验的要求。

用户数据与确定性业务状态由错题局官方后端管理；外部 OCR、语音和模型服务只作为可调用能力。普通用户不接触供应商 API Key。BYOK、自托管和开发者独立部署不属于第一版范围，只有在出现真实需求后才重新评估。

## 后果

### 正面后果

- 用户注册后即可使用，不需要理解模型供应商；
- API Key 不进入客户端；
- 官方可以统一处理成本计量、额度、限流、重试和故障降级；
- 用户数据与复习状态不会被单一模型供应商的数据结构绑死；
- 第一版只维护一种主要部署路径。

### 负面后果与代价

- 官方需要承担 AI/OCR 费用和滥用带来的现金流风险；
- 后端、密钥、日志、计量和用户数据需要由项目持续运维；
- 供应商故障会直接影响官方产品；
- 后续增加 BYOK 或自托管时需要重新设计部分配置和支持流程。

### 风险、缓解措施与后续验证

- 风险：少数重度用户产生过高的 AI/OCR 成本。
  - 缓解：服务端统一计量、限流和设置合理额度。
  - 验证：用私测用户的真实调用量计算每位活跃用户成本。
- 风险：供应商锁定。
  - 缓解：业务数据保存在自有数据底座，供应商通过轻量适配边界接入。
  - 验证：在正式选型前用同一组样本评测至少两种候选能力。
- 风险：官方服务故障导致用户无法使用 AI 链路。
  - 缓解：保留基础题目浏览、人工确认和复习状态操作的降级路径。
  - 验证：为 OCR、语音和模型分别定义超时与失败时的产品行为。
